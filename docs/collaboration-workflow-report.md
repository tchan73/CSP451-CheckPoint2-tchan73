Collaboration Workflow Report
1) Issues Created

GitHub Issues were disabled on the forked repository used for this assignment. To work around this limitation, issues were simulated and referenced inside Pull Request descriptions to demonstrate proper issue-to-PR workflow.

The following simulated issues were used:

Issue #1 – User Authentication Feature
Requested improvements to the login form, including input validation, inline error messages, and disabling form submission until inputs are valid.

Issue #2 – Database Connection Module
Requested documentation and setup notes for the database connection logic used by the application.

Issue #3 – API Endpoints Feature
Requested documentation and validation of API endpoints, including health and user routes.

Each Pull Request included a reference such as “Closes #1 (simulated – issues disabled on fork)” to demonstrate traceability.

3) Review Simulation Evidence

Each Pull Request received at least two review comments to simulate peer feedback. Comments focused on clarity, documentation purpose, and alignment with feature requirements.

The API Endpoints PR was used to demonstrate “Request changes”. Review feedback asked for clearer explanation of how the documentation related to API endpoint requirements. The requested change was addressed by updating the documentation and pushing a follow-up commit. Reviews were then re-requested and approved.

Before merging, all PRs were reviewed to ensure documentation accuracy, checklist completion, and consistency with the simulated issues.

4) Merge Strategy

All Pull Requests were merged into main using Squash and merge.
One key benefit of this approach is a clean commit history, where each feature appears as a single, meaningful commit, making the project easier to review, maintain, and audit.
